# Standalone provisioning build preset

Date: 2026-09-19
Related plan: docs/plan/2026-09-19-provision-build-preset.md

## Summary

Added a `provision` preset that builds the provisioning application as a
firmware of its own, with logs, into `cmake_gcc/build-provision/`:

```sh
cd cmake_gcc
cmake --workflow --preset provision
```

The application selection and the compile-time log floor became validated CMake
cache variables, `XBEE_APP_SELECT` and `XBEE_LOG_LEVEL`, replacing the hardcoded
`XBEE_APP=XBEE_APP_PROVISION` that had to be edited in two places. Only the
selected application is compiled; `src/app/src/xbee_bringup.c` is not a
translation unit of the provisioning build at all.

The preset lives in a new, tracked `cmake_gcc/CMakeUserPresets.json`, not in the
Studio-generated `cmake_gcc/CMakePresets.json`.

**The default `project` preset produces a byte-identical image to the one it
produced before this change**, verified by SHA-256 of `.bin`, `.hex` and `.s37`.

## Motivation

Building a dedicated provisioning firmware meant hand-editing two lines of
`cmake_gcc/CMakeLists.txt`, once on the `xbee_provision` target and once on the
generated `slc` target, and remembering to put them back. Both applications were
named unconditionally in the source list, so a provisioning image was built from
sources that included the bring-up diagnostic.

`src/app/src/xbee_dump.c` was split into its own module for this change
(`docs/plan/2026-09-19-xbee-parameter-dump.md`), so that the shared boot
parameter dump survives the exclusion of either application.

### Why CMakeUserPresets.json

`cmake_gcc/CMakePresets.json` is generated by Simplicity Studio, so the PRIME
RULE forbids editing it, and it is git-ignored (`.gitignore:27`) because it
holds machine-specific SDK paths. A preset added there would be destroyed on the
next generation and would never reach another machine.

CMake reads `CMakeUserPresets.json` from the same directory automatically, and
presets in it may inherit from presets in `CMakePresets.json`. Studio never
writes it, and `.gitignore`'s `cmake_gcc/*.cmake` pattern does not match a
`.json`, so no `.gitignore` change was needed to track it.

Cross-file inheritance was tested rather than assumed: it works with the CMake
in use here, **4.4.2**. The `provision` configure preset therefore restates only
`binaryDir` and the two cache variables; the generator `Ninja Multi-Config`, the
toolchain file and `CMAKE_CONFIGURATION_TYPES=base` all still come from the
generated file. No field had to be duplicated.

The name is CMake's convention for a *user's* own presets, and such a file is
often left untracked. Tracking it here is deliberate, and the reason is recorded
in the `.gitignore` header and in `readme.md`.

### Source order is load-bearing

Found during verification, not in the plan as first written.

With the application sources listed as `${xbee_app_sources}` followed by
`xbee_dump.c`, the default image had exactly the same size in every allocated
section and exactly the same 906 symbols with the same sizes and types as
before, but 165 of those symbols sat at different addresses and the `.bin` hash
differed. The cause was link order: the order of the sources in
`add_executable()` decides where the linker places each function and constant.

Putting `xbee_dump.c` ahead of the selected application reproduces the
historical order with the unselected application removed, and the default image
came out byte-identical. The requirement is written in a comment above
`add_executable()` so a later reordering is a deliberate act rather than an
accident.

### The log level is passed as a macro name

`APP_LOG_LEVEL_MIN=APP_LOG_LEVEL_<name>` rather than the integer the name
expands to, so the build system holds no second copy of the numbering in
`src/utils/inc/app_log.h` that could drift from it. This is safe because
`app_log_config.h`, which defines `APP_LOG_LEVEL_MIN` under an `#ifndef`, is
included from `app_log.h` alone and below the level definitions; a grep of the
tree confirms there is no other include of it.

Verified in the generated `CMakeFiles/impl-base.ninja`: all three defines,
`APP_LOG_LEVEL_MIN`, `XBEE_APP` and `XBEE_AT_TABLE_NAMES`, appear on all 70
compile units, including `app.c`, which is compiled in the `slc` object library.

### XBEE_AT_TABLE_NAMES comment corrected

The comment said the human-readable AT command names cost "Roughly 2 kB of
flash". The measurement in `docs/history/2026-09-19-xbee-parameter-dump.md` is
58 892 minus 54 884, so the comment now reads **4008 bytes**.

## Simplicity Studio changes (made by the user)

**None, and none were needed.**

A build preset is not a HAL, pin or component setting. Nothing under `config/`,
`autogen/`, `xbee_provision.slcp`, `xbee_provision.pintool` or the generated
`cmake_gcc/xbee_provision.cmake` was read or written; no peripheral, pin, clock
or software component changed; every image links against the same unmodified
generated `slc` target. `cmake_gcc/CMakePresets.json` was copied into the build
tree to make the build work and was not edited. `git status` shows no
Studio-owned file modified.

**Build, host tests and static review. Nothing was run on hardware.**

`cmake --workflow --preset project` from a removed build tree. The baseline was
also rebuilt once to confirm the build is reproducible at all, which it is.

### The standalone image

`cmake --workflow --preset provision` succeeds with zero warnings and produces
all four artifacts in `build-provision/base/`.

`arm-none-eabi-nm` on the `.out` shows **no `xbee_bringup_*` symbol**. The only
match for "bringup" is `bringup_reads`, a static in
`src/services/src/xbee.c`: the facade's list of parameters to read during
bring-up, which belongs to the XBee facade and not to the bring-up application.

No `xbee_bringup.c` object exists anywhere in the build tree, so the exclusion
is real at the translation-unit level.

### The saving is zero, and that is the finding

| Image | text | data | bss |
| --- | --- | --- | --- |
| Default (`project` preset) | 58 892 | 480 | 261 664 |
| Standalone provision (`provision` preset) | 58 892 | 480 | 261 664 |
| Bring-up (`-DXBEE_APP_SELECT=BRINGUP`) | 53 236 | 480 | 261 664 |

The standalone provisioning image is **byte-identical** to the default image:
the same `.bin` SHA-256, `37b5ca5b...4791`.

The build already compiles with `-ffunction-sections -fdata-sections` and links
with `-Wl,--gc-sections` (`cmake_gcc/xbee_provision.cmake:132,133,175`), so
every byte of `xbee_bringup.c` was already being garbage-collected out of a
`XBEE_APP_PROVISION` image. Excluding the source removes work from the compiler
and removes the application from the build, but it frees no flash and no RAM,
because none was being spent.

What the change does buy is that the selection is now a build input rather than
a hand edit, that the provisioning firmware is built from provisioning sources
only, and that a wrong selection is a diagnostic instead of a silent fallback.

### The other selections

- `-DXBEE_APP_SELECT=BRINGUP` on top of the preset configures and builds
  cleanly, zero warnings. The image contains `xbee_bringup_init` and
  `xbee_bringup_process` and **no `xbee_provision_*` symbol**, so the exclusion
  works in both directions.
- `-DXBEE_APP_SELECT=NONSENSE` fails at configure time, exit code 1, with
  `XBEE_APP_SELECT is "NONSENSE". It must be PROVISION or BRINGUP.`
- `-DXBEE_LOG_LEVEL=LOUD` fails at configure time with
  `XBEE_LOG_LEVEL is "LOUD". It must be one of: VERBOSE, INFO, WARNING, ERROR, NONE.`
- `-DXBEE_LOG_LEVEL=VERBOSE` builds cleanly and the define reaches every
  compile unit, but the image is the same size as the `INFO` one. There is no
  `APP_LOG_VERBOSE` call site anywhere in `src/` today, so the level currently
  has nothing to add. The knob is in place for when there is.

### Host tests

8 suites, all passing, zero build warnings.

## Known limitations and follow-ups

- **Not run on hardware.** No image from this change was flashed or executed. The
  default image being byte-identical to the previously built one is the strongest
  statement available here, and it is a statement about the file, not the board.
- The standalone provisioning image is byte-identical to the default image, so
  there is currently no reason to prefer one over the other for flashing. The
  preset's value is in the build, not the output.
- `XBEE_LOG_LEVEL` has no observable effect yet beyond `APP_LOG_LEVEL_MIN`,
  because no `APP_LOG_VERBOSE` calls exist. `NONE` and `ERROR` do shrink the
  image; those were not measured.
- The `provision` preset pins `XBEE_LOG_LEVEL=INFO`, which is also the header
  default. If the default in `src/utils/inc/app_log_config.h` ever changes, the
  preset will keep this build at `INFO` and the default build will follow the
  header. That is the intent of pinning it, but it is a divergence to be aware
  of.
- `cmake_gcc/CMakeUserPresets.json` inherits from a file that is not in git.
  After a fresh clone the `provision` preset cannot be used until Simplicity
  Studio has generated `CMakePresets.json`, the same precondition the `project`
  preset already has.
